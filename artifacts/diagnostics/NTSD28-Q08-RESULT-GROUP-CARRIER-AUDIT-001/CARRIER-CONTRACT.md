## Proposed independent state

Keep `BattleResultsRuntimeState.Phase`, `Timer`, `Winner`, `TeamIds[2]`, `TeamCount` and table arrays as the existing two-side result-page/UI state. Do not resize `TeamIds` or use `HadBoth` to decide the native battle end. `ActivateSummary` currently resets the live guard, so native timer/outcome state must live outside that reset. In the Results runtime state, add explicit native flow fields with these semantics only after the exact prechange Record and RED tests:

- `NativeLivingGroupMask : ulong`: bits 1..39 represent the source's sorted distinct group vector; bit 5 is always zero. Before result timer starts it reflects the latest classification. At first terminal classification it latches and does not change merely because groups revive. The sole set bit is the source winner group; zero or multiple bits means no winner. A 64-bit mask avoids per-tick array allocation while preserving the native bounded group set.
- `NativeResultTimer : int`: zero while at least two groups live and no result has begun; increments once per accepted battle tick after the first terminal classification. It is not reset by later revival. At source timer 350 the emitted event carries 350, then the stored timer becomes zero.
- `NativeResultPhase` and `NativeTransitionState`: retain the phase/transition distinction after the timer resets at 350. They must follow the source 80, 101, 350 and mode-specific transition mapping. No pre-battle background count should be inferred as a mode-4 results-settings stage count.

The first producer should classify immediately before combat work in `NTSDBattleTickSystem.RunTick`, after the existing host projection needed by the classifier but before any entity hit or late update. Result-page input remains in its after-world owner. The producer may publish a milestone for a later host presentation step in the same tick; the later step must not reclassify or increment the native timer. This is an ownership contract, not an instruction to copy the C++ object model into Unity. Exact placement relative to `AdvanceBattleFlowTick`, mode-4 reserve spawning, and active Results-page processing must be proven with focused tests before implementation.

## Persistence and compatibility

`BattleRuntimeState.Reset`, result rematch and explicit session restart must clear native flow fields. Ordinary `ActivateSummary` must not erase them before source timer 350; new Results UI has a separate reset path. `BattleWorldRosterResultsSnapshotBuffer` captures/restores current Results state with schema 1, while `BattleStateSnapshotBuffer` carries it under parent schema 25. Adding native flow fields requires a deliberate roster-results payload schema and parent snapshot schema update, restore preflight validation, replay tests for both timer-zero and timer-running states, and canonical mask validation (only bits 1..39 excluding 5). `BattleLockstepChecksumModule` currently uses schema 28 and hashes only the old guard/two-side fields; it must include the new carrier and bump its schema. `BattleParitySnapshot` must export native fields separately from result-page fields. Preserve existing two-side UI payload shape and unrelated protocol identity unless an actual protocol reader requires a change; reject stale payload versions rather than silently reinterpreting them.
