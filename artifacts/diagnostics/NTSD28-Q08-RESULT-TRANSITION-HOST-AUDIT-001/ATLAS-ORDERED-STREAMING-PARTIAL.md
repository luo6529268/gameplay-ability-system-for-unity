# Q08 ordered atlas page streaming — partial memory result

Change: `NTSD28-Q08-ATLAS-ORDERED-PAGE-STREAMING-001`. Before, the formal-content plan required 145 RGBA32 2048² pages and the ordered fallback retained all 2,432,696,320 CPU page bytes while creating textures. With opt-in trace, the baseline isolated Editor crashed while creating page 88, had no XML, sampled private bytes peaked at 18,015,555,584, and managed bytes at the last page begin were 6,156,177,408. See `ATLAS-ALLOCATION-TRACE-RESULT.md`.

The new branch only applies when the capability policy declines `Texture2DArray`. It assembles each page using the same plan placements, source pixels, one-pixel extrusion and upload arguments, instead of holding the `Color32[][]` for every page. The array-success path and array-attempt fallback still use the original whole-plan assembler. A two-page focused test compares every pixel of the new single-page assembler against the old whole-plan assembler. The isolated `BattleCommonAtlasBindingEditorTests` class produced `ATLAS-STREAMING-FOCUSED.xml` (SHA-256 `59C804AE4E165DAF6F62C811BF722279DA62114C375269DFA63DC8E5B6AA4EEE`) with 3/3 PASS, including existing array/common-binding tests. This proves the small fixtures and compilation; it is not full-content visual parity.

In the one formal-content isolated Scene rerun with identical content and opt-in trace, ordered page 118 completed and page 119 began before the same native `Could not allocate memory` crash. No XML, bootstrap completion or second-result assertion exists. External two-second sampling in `UNITY-SECOND-BATTLE-STREAMING-MEMORY.csv` observed peak private bytes 17,395,109,888, working set 12,698,251,264 and virtual bytes 43,410,010,112; the last page-begin trace reported managed bytes 4,877,156,352. Compared with the baseline, the measured memory peak was lower and the build advanced by 31 pages, but the 145-page publication remains blocked. These observations do not isolate CPU, system commit or GPU exhaustion. The 12 GiB GPU had 7,250 MiB used when queried after the crash; that is not a crash-time measurement and cannot be used as its cause.

The source-sheet `Texture2D` and `Sprite` objects are created and staged before atlas publication in `CharacterAnimtorManager.ProcessAndCreateSpritesForCandidateAsync`, and remain owned for runtime sprite rendering. Adding ordered atlas page textures therefore duplicates image residency during publication; the one-page CPU change does not remove that overlap. The existing `SourceTexture2D` central binding is a real runtime path for excluded/oversized sheets, but applying it broadly requires a separate explicit resource-policy and pixel/presentation acceptance task. Do not raise the texture-array budget or claim formal-content Q08 acceptance based on this partial improvement.
