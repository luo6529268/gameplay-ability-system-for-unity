# Q08 direct Battle Scene rematch implementation boundary

Status: `READ_ONLY_CALL_CHAIN_AUDIT`, 2026-09-22. This is an implementation boundary, not acceptance of a Unity rematch. Formal root EXE SHA-256: `B1E13AE17C86B77240B61A971AFD4C3374B645705F42B0BBCE304FD1D2819033`. No computer-use.

## Source behavior already measured

Formal `GameSession28::step()` consumes the first battle-only result transition 2 through `start_selected_battle`; `start_selected_battle` only admits a native upper-selection state-1 boundary and sets `battle_scene_only_loop=false` after successful recreation. It captures old dual RNG and `input_update_phase_4a0b90`, calls `initialize`, restores both, then resolves native BGM. The first-rematch source witness recorded old CRT state/calls unchanged, input phase 1 unchanged, and one synchronized draw at `0x004021E0` after restore. The next result reaches ordinary selection instead of another direct rematch; see `SECOND-CYCLE-SOURCE-WITNESS.md` and `RNG-PHASE-SOURCE-WITNESS.md`. This is a source-model contract, not formal EXE frontend pixel parity.

## Unity ownership now

* `SimulationTickDriver.TryDispatchOrdinaryResultTransition` routes any native transition 2 to `AppManager.TryReturnToCharacterSelectionFromBattleResult`. That method admits only `BattleRunning/BattlePaused` and requires both Menu and Battle scenes loaded. It correctly handles ordinary selection but cannot own a directly opened Battle Scene. The real Battle Scene D3D11 Play probe verified that the direct `AppManager [TestBootstrap]` is `MenuMain`, no Menu Scene exists and command 2 remains pending while the old tick freezes (`DIRECT-BATTLE-RESULT-PLAY-ACCEPTANCE.md`). Explicit battle-only ownership must be established by the direct Battle Scene entry, not inferred from a missing Menu Scene.
* `BattleTestBootstrap.Start` creates that AppManager if absent, asynchronously loads and validates formal content, prepares the map, calls `PrepareBattleRuntimeServices`, registers participants in private `SetupTestCharacters`, seals allocation, enables presentation and resumes the driver. `SetupTestCharacters` derives participant IDs and positions from its serialized override IDs and Battle Scene spawn points; it resets and repopulates the runtime roster. There is no post-result re-entry API or captured immutable direct-match configuration.
* `SimulationTickDriver.RecreateWorld` calls `ShutdownBattleRuntime`, `CompleteBattleRuntimeShutdownAfterMapCleanup(true)`, `CreateProductionWorld`, then `ResetDriverStateAfterWorldCreation`. It does not clear `BattleBootstrap`'s prepared map carrier, reprepare pool/factory, restore old RNG/input phase, register the roster, select BGM, seal allocation, enable presentation, or resume. Passing `true` is not evidence of map cleanup; a real same-scene rematch owner must clear that carrier between stages 10 and 11 or prove that it is already clear. A failed shutdown must leave gameplay stopped and must not proceed to recreation.
* `ApplyMatchConfig` resets the World, seeds `Rng` from config and calls `NativeRandom.ResetForDirectBattle(seed)`, which draws the first-boot BGM value. It is not itself a rematch transaction. The rematch must restore the captured previous `NativeRandom` state after any initialization reset and perform the measured BGM draw afterward. `SimulationWorld.Runtime.Flow.InputPhase` is the Unity carrier for the native input phase. A local `Rng` seed/reset must also be reviewed against native spawn RNG order; it cannot be assumed equivalent to the dual native state.
* Ordinary `AppManager.InitializeBattleAsync` has its own match/roster/scene path, including a separate `SetupBattleCharacters` with RNG-based positions. Reusing it for direct-scene rematch would change participant source, positions and AppManager lifecycle. `MatchConfig` currently has no explicit battle-only mode. Do not alter ordinary Menu selection behavior or nonbattle UI to recognize the direct scene.
