# Q09/P-13 Unity background consumer boundary (read-only, 2026-09-27)

The fresh current-content paired Session witness proves an actual Han147/Lee0 kind-3 catch can publish background (+2,0) then (0,0). It does not prove root EXE pixels or Unity output. This note maps the current Unity implementation seam; no production edit or runtime test was made.

- The searched Unity `Simulation`, `App` and `Animation` production paths contain `SessionEarthquake` only as a pass-order descriptor in `NTSD28BattlePassOrder.cs:356-358`. No battle earthquake state producer or background-offset consumer was found in those paths. The descriptor alone cannot move the project background.
- `SimulationStageRenderModule.RenderDispatchAll` starts `BattlePresentation.BeginFrame(world,tickIndex)` and queues the published frame (`:379-422`); `SimulationTickDriver.LateUpdate` consumes worker publication and calls `world.PresentLatestFrame` (`:490-509`). A future offset must be published with the completed tick and kept separate from entity logical coordinates so the worker and local paths display the same tick.
- `BattleBootstrap` owns the project map sprite binding in `backgroundRenderer` (`:30,80-98,117-118`). `BattleBackgroundPlatformPresentation.TryApplyWorldCameraFrame` derives the fixed camera frame from `sourceRenderer.bounds` (`:283-309`). A visual offset that changes those bounds before any `RefreshPresentation` would change the camera frame too. The display seam must preserve a neutral source bound for camera framing and apply earthquake only to background drawing; moving the global camera, battle entities or map boundary carrier is outside the formal behavior and user exception.
- The formal paired renderer consumes `snapshot.earthquake.background_offset_x/y` only in background drawing, while `NativeEarthquake28::step` updates owner/offset after the full World step. The Unity producer therefore needs a stateful owner/offset handoff with the formal slot scan and reset semantics, rather than a one-frame stateless animation. A new production Task/Change must define reset/shutdown, worker publication, fixed-camera and background/entity isolation tests before scripts change.

Additional producer-placement finding: `NTSDBattleTickSystem.RunPresentationAndCleanupPhase` calls `RenderDispatch` after stage/results work (`:513-579`), including a branch where `buildPresentation` can be false. `RenderDispatch` skips worker frame capture when that flag is false (`:759-771`); `SimulationStageRenderModule.RenderDispatchAll` also skips `BattlePresentation.BeginFrame` on the CentralOnly no-build path (`:379-426`). Thus a stateful earthquake owner cannot advance **only** inside `BattlePresentationCoordinator.BeginFrameCore`: it would miss successful simulation ticks with no published frame. The producer belongs in a once-per-successful-tick post-World seam, with its state copied into any frame that is published. `BattlePresentationFrame` already freezes/copies other scalar/array presentation values (`BattlePresentationShadowBuild.cs:978-1186`) but has no earthquake values yet.

Snapshot boundary: `SimulationWorld.RebuildDerivedStateAfterSnapshotRestore` calls `BattlePresentation.Reset()` (`SimulationWorld.cs:1090-1142`). Formal `NativeEarthquake28` retains X/Y offsets when its owner leaves a 5xxxx state (`render_snapshot.cpp:1060-1097`). An implementation that stores only those scalars in the presentation coordinator would erase them on replay/restore; an implementation that recomputes from the current frame would lose retained values. The production Task must declare snapshot/restore ownership for owner and X/Y offset, and verify a restore across an owner-release tick, as well as normal reset/shutdown. This is a required data contract, not an optional visual polish step.

Remaining evidence: root formal EXE natural keyboard action0-to-skill and same-tick visible background output; original Unity Battle Scene selected skill and pixel A/B of background versus entities; any user-approved visual exception interaction. The current full-Session witness is sufficient to prioritize the producer/consumer gap but is not a claim that P-13 or Q09 is aligned.
