# D-024 continuous source-rule motion gate

2026-09-24 read-only caller audit for the next priority after the bounded continuation-effect birth. The existing source-rule carrier is birth/snapshot/checksum capable but its continuous motion is not active. This note does not implement movement or certify all physics branches.

Formal playable `ntsd28_core/src/simulation/physics_integrator.cpp` is included by the playable build. `PhysicsIntegrator28::step` adds unscaled `motion.x` to precise X unless the source-domain directional flag blocks it, applies independent type4/ID120 positive 20% and ID101 negative 20% X extras, adds unscaled `motion.z` unless the corresponding source-domain flag blocks it, and adds type3 `frame_hit_j-50` Z when applicable. The common tail calls `synchronize_integer_coordinates` after integration, truncating the resulting precise X/Z toward zero. Grounded friction follows position integration, so stored velocity is not the same as that tick's displacement. Formal source flag publication and clearing must be traced through the collision pass and consume boundary before using this history in gameplay readers.

Unity physical output already multiplies actual travel by D-024 viewport ratios in the active character and non-character `CharacterMechanics.StepBattleLogic`, `WeaponDynamics`, and `StepNonCharacterBattleLogic` paths; `BattleEcsCharacterFrameAdvancePass.ExecuteCharacterDynamics` and `LF2Entity.RunSharedCharacterDatFrameAdvanceAsCharacter` call these and synchronize battle integers afterward. `LF2Entity` also has non-character direct frame/identity movement paths around 5900 and 6900–6955. None of these continuous paths currently advances `SourceRuleX/Z`; source integers remain at birth for moved entities. A source reader activated now would observe stale positions, explaining why ordinary revival average, OID219 and fusion cannot switch merely because birth fixtures pass.

Additional 2026-09-24 read-only inventory: the direct runtime X/Z writers are not limited to the shared mechanics helper. `LF2Entity.RunSharedNonCharacterDatFrameAdvance` writes scaled identity-X extras and type-3 `hit_j` depth before the shared mechanics call; `ApplyLinkedPlatformMotion` and `ApplyNativeFrameMotionTail` write scaled positions from integer bases and round their integer mirrors before physics. Formal `battle_world.cpp:1675-1795` applies the corresponding platform and frame positional motion to source coordinates before `PhysicsIntegrator28::step`, then the latter integrates velocity and truncates integer mirrors. Implementing source motion only in `CharacterMechanics` would omit these source moves and alter the next tick's source integer base.

The kind-14 collision flag is also domain-dependent. Formal `battle_world.cpp:5542-5578` compares attacker and target *source integer* X/Z with raw `+/-5` and `+/-2` thresholds, writes one-tick directional flags, and `battle_world.cpp:1962-1964` clears them when physics consumes them. Unity `BattleBoundaryWriter.TryApplyKind14DirectionalBlock` currently compares physical precise positions and writes only physical flags; multiple fallback hit paths call the same writer when a world exists. A source physics writer must therefore receive its own source-domain flags from that producer and clear them on the same consume boundary, without substituting the viewport-scaled physical flags.

Other physical position writers found by scoped search include held-object/cpoint mounts, kind-8 control, interaction separation, OID51/52 fusion, AI candidate probes, spawn and stage bounds. These are candidates for separate source-domain audits, not evidence that every assignment should be multiplied by the view scale. In particular, source-rule gameplay readers remain gated until source motion, flags, and these explicit rebases are handled at their formal call boundaries.

2026-09-24 pass-order follow-up: formal `SimulationTickDriver28::step` calls `BattleWorld28::apply_frame_motion` for active slots, then state-400/401 teleport, then per-slot `step_physics`, followed by revival and stage depth. The formal frame-motion transaction applies linked-platform precise/int position writes first, then direct `dx/dy/dz` position writes from the *current integer* base, and only later does physics integrate velocity and truncate the final precise X/Z. Physics can return before integration for motion-hold, negative interaction relation, or suppressed frame. Unity `NTSDBattleTickSystem.RunFrameAdvancePhase` has the same broad FrameMotion → NativeTeleport → NestedPhysics → Revival → StageBounds order; `SimulationWorld.NativeFrameMotionAll` calls each `LF2Entity.ApplyNativeFrameMotionForWorldPass`, and `NativePhysicsAndDeadCharacterResourceNormalizeAll` selects the ECS type-0 character path or entity fallback. Preserve these early-return gates and integer-base timing in source history; a single post-tick inverse transform would erase them.

Unity motion ownership is now narrowed: active type-0 ECS uses `BattleEcsCharacterFrameAdvancePass.ExecuteCharacterDynamics` → `CharacterMechanics.StepBattleLogic` → final `SyncIntegerPosition`; fallback `LF2Character.ApplyDynamics` calls the same mechanics.
