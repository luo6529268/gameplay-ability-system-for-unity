# D-024 all-entity motion: initial production-path inventory

Status: `LEXICAL_CENSUS_ONLY / SEMANTIC_CLOSURE_PENDING` (2026-09-23). This is a working inventory, not a claim that every reachable movement writer has been enumerated or changed. DAT bytes are outside the edit scope.

## Projection evidence and current sample

- Formal playable `RenderCamera28` defaults to width 1333 and height 730 (`source/ntsd28_core/include/ntsd28/render_snapshot.h:566-571`). The formal render snapshot projects an entity's screen top from `position.z + position.y` before the frame center offset (`source/ntsd28_core/src/rendering/render_snapshot.cpp:1722`). The exact visible travel also depends on camera motion, clipping and the render sample.
- Current Unity Training fixed-camera 16:9 sample, measured in the preceding run package, exposes 2048 px horizontally and 1152 px vertically. The sample target factors are therefore `Sx=2048/1333=1.536384...` and `SscreenY=1152/730=1.578082...`. Unity `NTSDRenderSpace` maps ground X/Z to screen axes; `CharacterMechanics` also projects airborne Y. `NTSDRenderSpace.SourceScreenWidth=794` / `SourceScreenHeight=550` are older mapping constants, not the formal release viewport.
- These factors are **sample-specific**. For other aspects/maps, inspect the actual fixed camera viewport and the formal camera behavior before selecting factors. A camera-follow phase can change visible displacement despite equal world travel. Scaling both `Y` and `Z` by the vertical factor is a candidate derived from their screen projection, not yet a complete collision/height contract.
- Current production setup is a serialized Training reference, not a live viewport measurement: `GameConfig.asset` stores `BattleFixedViewRunReferenceWidthPx=2048` and `BattleFixedViewRunReferenceHeightPx=1152`; `SimulationTickDriver` forwards them when configuring the World (`:2439-2441`, `:2516-2518`). `SimulationWorld.ConfigureFixedViewRunDistance` (`:76-85`) clamps each factor to `1` whenever that reference axis is at or below the formal 1333/730 value. Thus alternate screen sizes/aspects, and any target fraction below one, are **not covered** by the current implementation. Do not call a single configured Training sample a dynamic all-viewport ratio policy; measure real projection and define the small-view case before that gate can close.

## First-difference and implementation dependencies

The existing character run/dash slice initially applied horizontal `Sx` to ground-depth Z. Z projects vertically in both paths, so that slice was corrected to `SscreenY` in `NTSD28-USER-FIXED-VIEW-RUN-RATIO-001`. The newer core-output slice removed early run-speed multipliers and applies X/Z ratios at the shared position integrator; the other entity movement categories and bypasses remain unimplemented. Do not stack a second multiplier on the same integrated delta. Preserve raw DAT values and original transition timing. Collision geometry, attack reach, AI pursuit, stage clamping and attachment offsets require explicit result checks after a change to actual world travel.

## Semantic follow-up: velocity is also gameplay state

The earlier character run/dash slice multiplied `Runtime.Vx/Vz` *before* physics. Formal `PhysicsIntegrator28::step` (`physics_integrator.cpp:52-58, 105-112`) integrates pre-friction motion and then damps stored motion by one unit. Unity `CharacterMechanics.StepBattleLogic` has the same ordering. With authored horizontal motion 18 and this sample's `Sx`, the early multiplier produced stored post-friction motion `18*Sx-1` instead of formal `17`. `NTSD28-USER-CORE-MOTION-OUTPUT-RATIO-001` has since removed that early scaling and moved the first X/Z adaptation to the shared integrated position delta. Its focused mechanics checks prove the configured position and raw post-friction velocity for character and non-character examples. They do not prove full `SimulationTickDriver` tick, every direct writer, real Play or other viewports.

The core integrated travel is **not a single method**. Character `StepBattleLogic` has three observed production callers (`LF2Character.cs:166`, `LF2Entity.cs:5604`, `BattleEcsCharacterFrameAdvancePass.cs:126`). Non-character `StepNonCharacterBattleLogic` is called by `LF2Entity.cs:5908` and `LF2WeaponBase.cs:944`; `LF2WeaponBase.cs:978` also calls `WeaponDynamics`. These methods all write X/Z/Y and apply friction. `LF2Entity.RunSharedNonCharacterDatFrameAdvance` writes identity X extra and type-3 `hit_j-50` Z *before* the generic integrator (`LF2Entity.cs:5880-5908`), so simply changing the generic velocity integration still leaves direct displacement unscaled. `LF2Entity.ApplyInitialRuntimePosition` (`:5037-5055`) installs absolute OPoint positions, and `object_spawning.cpp:109-128` shows parent-relative spawn X/Y/Z plus one Z unit, then separate launch motion. Attachment/throw writers such as `BattleHeldObjectWriter.cs:150-228` and CPoint/Interaction writers use both absolute placement and velocity assignment. They cannot all share a blind numeric multiplier: relative offsets and actual travel need the same coordinate policy, while logical velocity, frame timing and authored DAT remain raw.

Concrete next implementation gate: verify the new production caller wiring in a complete `SimulationTickDriver` tick and real Battle Scene for one character and one non-character, then enumerate the remaining direct movement bypasses and define how scaled collision positions/extent, stage bounds, OPoint offsets, held attachments, teleport, Y altitude and independent render offsets interoperate. A direct-spawn/interaction witness is still missing. The existing first slice must not be mistaken for full D-024 coverage.

Updated focused evidence: a configured synthetic `NTSDBattleTickSystem.RunReleaseTick` core tick passed 1/1 in the original Unity Editor (job `87a7cee42fff4f4d97010c02e07a1096`), and a production-materialized type-1 weapon non-character physics pass passed 1/1 (job `e5279a84494743079e17e45da450389c`). The first full core-tick fixture started at Z=100 and was clamped by the later stage-boundary pass to the scene minimum Z=180; the successful case starts at legal Z=250. This is evidence that stage bounds must be explicitly reconciled with the new position ratio. Both witnesses are synthetic, and neither substitutes for live `SimulationTickDriver`/Battle Scene or formal EXE screen-travel comparison.

## Late OPoint placement: first classified bypass (2026-09-23)

The formal `ObjectSpawnPlanner28::plan_frame` (`source/ntsd28_core/src/simulation/object_spawning.cpp:77-153`) creates a child's integer X/Y/Z from the parent's position plus a facing-dependent frame-center/OPoint offset; Z also has a native `+1`. It assigns launch motion separately from placement. Unity has **two** production late-OPoint owners: `BattleLogicObjectPointRuntime.ConfigureLateOpointPosition` (`Assets/NTSD/Scripts/Simulation/Runtime/BattleLogicObjectPointRuntime.cs:316-339`) and component `LF2ObjectPointFactory.ConfigureLateOpointPosition` (`Assets/NTSD/Scripts/Animation/Character/LF2ObjectPointFactory.cs:341-363`). Both mirror this formula with parent integer position and raw OPoint offsets, then write direct precise and initial integer positions into `OPointCreateTask`. `BattleLogicEntityFactory.PrepareFinalRuntimePosition` (`:248-272`) forwards direct positions and conditionally applies its own `+1`; `LF2Entity.ApplyInitialRuntimePosition` (`:5027-5046`) installs the resulting absolute coordinates. Ordinary integrated movement scaling cannot affect this birth offset. Existing `NTSD28Q06OpointMaterializerEditorTests` uses both World and component routes for default-scale source comparison; an implementation changing only one route would be incomplete.

The choice is an actual production branch, not just a dormant duplicate: `SimulationWorld.ResolveObjectPointFactoryForSimulation` (`Assets/NTSD/Scripts/Simulation/Core/SimulationWorld.cs:758-765`) selects the logic runtime when `logicOnlyEntityMaterialization` is true and the component singleton otherwise. `ResolveLateObjectPointStructuralMaterializerForModule` (`:2395-2400`) forwards that selected factory to the late structural pass. Both routes therefore need the same D-024 offset contract and configured-World tests.

Other `ReleaseSpawnSemantic` producers and branches (including state-18 particles, clone, remaining immediate/transition effects and respawn position updates) remain unclassified here. This table is a semantic increment over the lexical census, not a completeness claim.

This is a **parent-relative placement delta**, not another velocity integral. On a configured scaled World, the parent can already have scaled travel while the OPoint offset remains an unscaled DAT pixel count; a child therefore starts at the wrong screen fraction even though its next physics step uses the new scale. Blind multiplication of final child absolute X/Z would also multiply the already-scaled parent position and shift the whole scene. The next bounded slice must scale the *difference from the parent* once, including the native `+1` depth delta, preserve raw launch velocity, and keep precise/integer child coordinates coherent. It must distinguish late OPoint from immediate effects, stage spawns, random drops, weapon pieces, respawns and direct absolute task positions; those are separate producers listed in `spawn-motion-write-census.txt`. This is a source-path diagnosis, not a validated runtime first difference or permission to scale every spawn task.

## Stage-boundary interaction that follows scaled travel

Formal `BattleWorld28::clamp_type0_stage_depth` (`battle_world.cpp:8083-8111`) clamps every active object's precise Z to stage near/far, with non-type-0 entities receiving one raw unit of margin on each side; it always refreshes integer Z afterward. Its ordinary bounds pass then applies type-3 offstage culling against stage width plus raw margins. Unity `SimulationStageRenderModule.ClampCharacterZToStageBoundsAll` (`:240-262`) and the ECS `BattleEcsCharacterStageZPass` consume configured `Runtime.Stage.ZMin/ZMax`, while `RunLegacyPreFrameBoundsAll` also reads stage width and X override. The configured full core-tick motion test already observed the Z=100→180 clamp. D-024 makes actual X/Z travel larger while these thresholds stay raw in the current sample, so stage arrival and culling need a separate coordinate-domain decision and same-tick tests; merely passing an in-range movement sample does not settle boundary parity. This finding is read-only and does not authorize changing stage DAT, GameConfig, map dimensions or stage rules as part of the late-OPoint slice.
