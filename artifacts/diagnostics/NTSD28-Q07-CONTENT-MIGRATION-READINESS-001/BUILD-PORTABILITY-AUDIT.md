# Q07 portable Player content audit (2026-09-22)

> **Current update:** Windows Mono Player packaging has since passed an actual BuildPipeline build and exact 1,343-file sidecar SHA audit, documented in `WINDOWS-PLAYER-PACKAGING-ACCEPTANCE.md`. The original source-audit status below is historical; actual Player startup with formal content remains unverified.

Status: `PACKAGING_GAP_CONFIRMED_BY_SOURCE / PLAYER_NOT_BUILT`. This is a read-only architecture finding, not a build or runtime certificate.

The project-local staging root is `Assets/NTSD/Content/LoganRuntime`. `CharacterAnimtorManager.ResolveConfiguredLoganSource` resolves a configured relative root against `Application.dataPath/..`, while `BattleContentSource` uses direct `File`/`Directory` reads of `catalog.csv`, `decoded_dat` and `vfs`. `GameConfig.asset` still has an empty battle-content root. A search across the current `Assets/*.cs` found no `BuildPlayerProcessor`, `AddAdditionalPathToStreamingAssets`, post-build copy, or other packaging path for this root. Existing Windows BuildPlayer entry points merely call `BuildPipeline.BuildPlayer` with selected scenes. Therefore the current source proves Editor-local candidate access but supplies no evidence that a Player can find the same raw directory; Q07 must not activate production based on Editor tests alone.

Unity 2022.3 documents that ordinary Scenes/Assets are combined into Player data, while `StreamingAssets` files are copied verbatim and reached through `Application.streamingAssetsPath` ([Unity Streaming Assets manual](https://docs.unity3d.com/cn/2022.3/Manual/StreamingAssets.html)). Unity also provides `BuildPlayerContext.AddAdditionalPathToStreamingAssets(existingDirectory, destinationPath)` to include an existing source tree without first placing a duplicate under the project's StreamingAssets folder ([Unity 2022.3 API](https://docs.unity3d.com/ja/2022.3/ScriptReference/Build.BuildPlayerContext.AddAdditionalPathToStreamingAssets.html)); that context comes from `BuildPlayerProcessor.PrepareForBuild` ([Unity 2022.3 BuildPlayerContext](https://docs.unity3d.com/cn/2022.3/ScriptReference/Build.BuildPlayerContext.html)). These are **candidate implementation mechanisms**, not a claim that this project currently invokes them.

Proposed exact next contract for a separate Task/Change: retain the single staged source tree, add a build callback that includes it at a fixed Player StreamingAssets child path only when the battle config selects the formal bundled source, and make the battle-content resolver map that selection to the project-local staging root in Editor and `Application.streamingAssetsPath` in supported desktop Players. Preserve the Q02 explicit external-root and empty-root legacy behavior, refuse a missing/incomplete manifest instead of falling back silently, and validate the complete 1,343-file set and content fingerprint in an actual built Player. Android/WebGL expose StreamingAssets as URL-backed paths and cannot use this direct `File` loader; they need an explicit separate implementation before those targets are claimed. No mobile/WebGL Player acceptance is implied by Windows Editor tests.

The alternative of copying a tree manually next to one Windows executable might pass on that machine but would leave the repository's normal build path and other platform semantics unsolved. No path relocation, duplicate copy, build callback, resolver edit, Player build or GameConfig switch was performed in this audit. This remains a production-switch gate alongside full publication and actual App/menu caller checks.

## Follow-up after staged Editor Play (2026-09-22)

Actual App/menu Editor Play and real owner shutdown now pass under `NTSD28-Q07-STAGED-FORMAL-CALLER-PLAY-001`; see `STAGED-CALLER-PLAY-ACCEPTANCE.md`. This closes the Editor caller/lifecycle part of the gate, not Player availability.

The existing Windows-only `ProductionEntityStressPlayerBuild.CopyRawBattleFiles` already demonstrates a separate portable sidecar layout: it copies legacy Config/Sprite under the directory beside the EXE and copies `SPARK.bmp` under `<player>_Data/NTSD/Sprite/UIPanels`. That method is specific to its stress-build entry point; the other BuildPipeline entry and ordinary Player builds do not call it. The configured Logan resolver currently maps the relative `Assets/NTSD/Content/LoganRuntime` root against `Application.dataPath/..`, so a **Windows sidecar** at `<exe directory>/Assets/NTSD/Content/LoganRuntime` could preserve the current resolver without a runtime change. This is an implementation candidate, not a verified Player result. A normal-build integration path and complete manifest check are still required; copying only the EXE without the sidecar would fail. `BuildSparkPublicationAsync` separately reads raw `Application.dataPath/NTSD/Sprite/UIPanels/SPARK.bmp`, so a formal-content Player validation must also account for that existing non-D-023 battle visual dependency. Do not silently expand the D-023 image migration or delete its old source.

The next independent Task must choose and declare the supported Player distribution contract (StreamingAssets with a resolver mapping or a Windows sidecar) and validate the exact output, startup source selection and full publication in an actual built Player. The current audit does not justify changing the production GameConfig yet.
