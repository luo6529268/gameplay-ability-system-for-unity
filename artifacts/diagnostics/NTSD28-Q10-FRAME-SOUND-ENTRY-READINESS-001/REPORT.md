## Actual Q10 open boundary

`SimulationTickDriver` copies pending events after checksum into the presentation queue and calls `NTSDSoundPlayer.PresentSounds`. That player resolves cues through `AudioController` or a fallback under `Assets/NTSD/Sound`; whether each formal cue resolves to an actual clip, has the right ordering/channel/attenuation and is audible in a formal-content battle has not been established here. The Q07 inventory already reports 13 missing legacy audio directories; D-023 authorizes DAT and character images, not a blanket WAV replacement. Q10 should start with a cue-to-source-path and playable-event inventory, then compare actual presentation/volume/BGM/stop behavior. Do not reimplement the Q06 frame-sound producer or treat queued events as audible output.

An initial **lexical path inventory** is now in `formal-indexed-cue-paths.csv` (SHA-256 `C2331CB3423CEFCCEC78FD8A53BE61E93937FA2423D8F07E3C2593808D79ACCB`). It reads exactly the 330 `object` rows of the formal `resources/runtime/catalog.csv`, all of whose decoded DAT paths exist, and extracts `sound:` values ending in `.wav`, `.ogg` or `.mp3`. Those files contain 8,864 such declarations and 976 distinct cue paths. All 976 resolve under formal `resources/runtime/vfs`; 71 resolve at the same relative path under Unity `Assets/NTSD/Sound`, leaving 905 without a matching local file. The CSV records declaration counts and owning object IDs. Six other distinct numeric `sound:` values were observed in ITR records and excluded from this **file-path** inventory; this lexical inventory is not a parser-normalized frame/event count or a proof that every declared cue is reachable during play. `AudioController` may provide configured clips for missing paths, so 905 missing local files does **not** mean 905 proven silent cues.

The next Q10 step is to join these paths to the typed frame declarations and runtime event sources, classify existing `AudioController` clip overrides, then verify actual clip playback. Do not silently copy all formal WAVs: their authority/deployment boundary is separate from D-023.

The current serialized `Assets/NTSD/Scene/NTSD_Battle.unity` has one enabled `AudioController` using the GUID of `Assets/NTSD/Scripts/App/AudioController.cs`, and its `AudioList` is `[]` (Scene line 5692). A scoped scan of `Assets` found no other serialized reference to that script GUID; a scoped scan of project scripts found no assignment to `AudioList`. `AppManager` adds `NTSDSoundPlayer` at runtime; its default `soundRootFolder` is `NTSD/Sound`. `GetOrPrepareCue` therefore falls back to the cue itself as the relative path when this scene's empty controller is active. `LoadSingleAudioClipAsync` returns no clip on a file load failure, and `PlayPreparedCue` returns when `PickClip` finds no clip.

For **this serialized direct Battle Scene and current local files**, the 905 missing same-path cues have no configured `AudioController` clip fallback. That is a static source-path/clip gap, stronger than the inventory alone. It is not a measured count of audible failures: a given cue must first be emitted by gameplay, and a running player could have different sidecar files or an externally injected controller. Menu-to-Battle lifecycle, the 71 existing cues in a built Player, actual playback and formal EXE sound comparison remain unverified. The implementation choice between declared external formal VFS audio, selected asset deployment and an explicit exception requires its own bounded Q10 Task/Change and validation; this audit does not make that choice or change audio files.

The formal playable path supplies the authority for a future routing decision. `main.cpp::audio_roots` places `complete_vfs_root/decoded_dat` and then `complete_vfs_root/vfs` before the extracted-root fallbacks. `AudioResourceResolver28::resolve` normalizes backslashes and selects the first regular file under those roots; `XAudio2Backend28::submit` resolves each event's declared resource path before decoding and playing it (`main.cpp` lines 144-153; `audio_backend.cpp` lines 406-425, 503-604). Unity already has a battle-only `GameConfig.BattleContentRuntimeRoot` and `CharacterAnimtorManager`'s published Logan content source for DAT/images, but `NTSDSoundPlayer` currently ignores that root and uses `Application.dataPath/NTSD/Sound`. **The current staged `Assets/NTSD/Content/LoganRuntime/vfs` contains zero WAV files**, so pointing audio at that root alone would not solve this gap. A bounded Q10 implementation must first declare either an available external formal VFS or a scoped audio deployment, together with lifecycle, path safety, clip caching/teardown, Player sidecar and event/playback parity. Neither route has been implemented or tested here; D-023 does not authorize blanket WAV copying.

The 71 overlapping paths were checked more deeply, with no resource changes. `overlap-71-sha256.csv` (SHA-256 `F925DC3F932BECD21F9702CF9B43D76E8CF4D36E33750DE958BE91CA9DEC0DA1`) shows **0/71 identical whole-file hashes**. All 71 pairs parse as PCM WAV. `overlap-71-pcm-sha256.csv` (SHA-256 `BE96A9F4B8E64004B6EF1BAF0A047F16CACC6A5195ADA4A2AAB9B612B2694410`) shows **28/71 identical PCM frame bytes, 43/71 different**. `overlap-71-wave-metadata.csv` (SHA-256 `2246FDB023DDBC99635BDF7BD2CB69290283B16CB7157995A022603843D2B7BB`) shows **17/71 different duration in milliseconds**. Whole-file differences can come from WAV headers, but 43 PCM differences cannot be dismissed as header-only. These are content differences, not a measured audible A/B result or proof that any particular cue fires during a battle. The current Unity sound folder therefore cannot be accepted as formally identical merely because 71 paths overlap.
