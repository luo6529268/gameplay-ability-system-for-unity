## Observed routing

- The serialized `GameConfig.asset` selects `Assets/NTSD/Content/LoganRuntime`. `LoadingPrewarmController.PrewarmOnceCoreAsync` routes a nonempty configured root to `PrewarmConfiguredLoganContentAsync`; its old `CreateCharacterConfigTask` and `CreateCharacterSpriteTask` path is the empty-root branch. Both task bodies also reject `HasConfiguredLoganContent`. Thus the old DAT/sprite prewarm is not the configured default caller, although the legacy fallback and tests remain.
- `GameDataManager.InitializeSingleton` unconditionally calls `LoadDataFile()` with the old `Assets/NTSD/Config/data.txt` default. Formal `PrepareObjectPublication` then replaces the object definitions with the Logan candidate but copies `cachedConfig.backgrounds`; `CommitObjectPublication` does not replace `backgroundLookup`. The old file is therefore still a reachable initialization input even with the formal root selected. Removing it now would also break the retained empty-root fallback and emit a missing-file error.
- The current old `data.txt` has no `<background>` block or background rows. The formal `resources/runtime/decoded_dat/data/data.txt` has a `<background>` block and 24 rows (IDs 0–23). These are content-file observations, not proof that the formal EXE necessarily exposes all 24 in every mode.
- The formal playable `game_session.cpp` calls `load_native_background_dat_paths(decoded_dat_root_)`. That loader reads the canonical `data/data.txt` background block, rejects missing/duplicate/escaping paths and fills an ID-indexed DAT vector. A fresh check found 24 unique IDs (0–23) and all 24 DAT paths present in the formal decoded root. `GameSession28::available_background_ids()` passes those nonempty IDs into `PostRosterMenu28`, which appends its random-background choice. This proves the playable menu catalog input, not a results-stage wrap count; no direct result-stage count transfer was found in this read path.
- `SimulationTickDriver` assigns `Match.RuntimeStageCount = GameDataManager.TryGetInstance()?.BackgroundCount ?? 0` during battle preparation. With the old manager file and formal object publication, this count is 0 unless another path changes the manager state; the searched production C# has only this assignment. `BattleResultsWriter` advances to the random-stage sentinel `0x64` only when `RuntimeStageCount > 0` and the incremented stage reaches that count. The static source path therefore exposes a Q08 stage/result behavior candidate difference. A focused runtime/source-matched test is required before claiming the observable result.
- `GetBackgroundById` has no non-test C# caller found in the current `Assets/NTSD/Scripts` search. `BackgroundCount` is consumed by the battle host; background definitions are not proven to be the renderer's source. Do not equate this finding with a mandate to replace every background image.
