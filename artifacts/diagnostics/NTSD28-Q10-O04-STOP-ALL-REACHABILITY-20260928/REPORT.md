## Two different stop-all owners

1. **Story result event.** `GameSession28` sets `native_story_phase_runtime_.result_audio_stop_pending` when a story mission completes and its result timer first reaches 1 (`game_session.cpp:1826-1844`). At the successful step tail it appends one `WorldAudioEventSource28::story_result_stop_all` event and clears the pending flag (`:3285-3291`). `XAudio2Backend28::submit` consumes that event in list order and calls `stop_all()` before processing later events (`audio_backend.cpp:525-530`). `stop_all()` stops and destroys active SFX voices, then clears their list (`:699-705`); it does not stop the separate BGM voice (`stop_bgm` is `:707-713`). The same story branch clears `selected_bgm_virtual_path_`, which the outer `main.cpp` synchronizes via `start_looping_bgm` (`main.cpp:2331-2342`, `:2538`, `:2586`). These are two distinct operations.
2. **Root host reset.** The window input branch accepts non-function `R` when recording is not save-pending and sets `reset_requested` (`main.cpp:2011-2017`). The host loop calls `app.audio.stop_all()` immediately before `app.session.reset(...)` (`:2481-2489`). This is a host reset, not a `WorldAudioEvent28` on an ordinary battle result tick. The same `stop_all()` only clears SFX; the host's BGM selection/synchronization remains separately owned.

The current shipped-root story selector caller audit at `artifacts/diagnostics/NTSD28-Q08-RESULT-GROUP-CARRIER-AUDIT-001/STORY-SELECTOR-CALLER-CORRECTION.md` finds no default-root menu/CLI writer for the required paired story mission and child IDs. Therefore the story-result stop-all is a **conditional playable rule without a proven entry from the current root's default selection flow**. Do not inject it into every ordinary result, and do not treat absence of that event from a mode-0 match as a Unity first difference. If a released story caller or project-selected story contract becomes reachable, reopen this exact event-order/BGM boundary.

The `R` reset route is a separately reachable formal host behavior. A current search of `Assets/NTSD/Scripts` found no production `KeyCode.R`, `Keyboard.current.rKey`, or `Key.R` battle binding; the existing `SimulationTickDriver.RecreateWorld()` callers found in that search are test/bootstrap or diagnostic paths. The current `NTSDInputConfig.inputactions` search found no `<Keyboard>/r` binding. This is a **static host-entry gap candidate**, not a measured same-input runtime/audio first difference: this audit did not exercise R on the root EXE or Unity, compare active-voice state, or test BGM/device output. The next O-04 action is to establish the exact reset/input policy and matched root-versus-Unity behavior before any battle-host change.
