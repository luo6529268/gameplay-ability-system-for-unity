# Q10 per-tick battle audio publication — read-only first-difference audit (2026-09-27)

Authority identity: formal root `NTSD2.8-Logan.exe` SHA-256 `B1E13AE17C86B77240B61A971AFD4C3374B645705F42B0BBCE304FD1D2819033` was rechecked. The paired playable source paths below are in its declared build closure. This report is a static source audit; no same-condition audible EXE/Unity capture was performed.

Formal host sequence: `source/ntsd28_playable/src/main.cpp:2525-2555` completes `app.session.step()`, submits frontend audio if present, calls `advance_native_volume()`, then `synchronize_bgm()`, then submits that tick's battle `audio_events` to `app.audio.submit(...)`. The paused F2 single-step branch at `2572-2599` uses the same ordering. The normal accumulator loop can run more than one successful logic tick before the outer present loop returns. Thus battle audio is handed to the backend separately for each successful tick after that tick's volume adjustment, even when multiple ticks occur in one display iteration. Frontend events have a different pre-volume submission position and must not be conflated with battle events.

Formal backend sequence: `source/ntsd28_playable/src/audio_backend.cpp:503-595` creates and starts a source voice during each `submit`, using the current percentage. `set_volume_percent` at `689-695` immediately calls `apply_volume_gains`; `460-473` retunes *all active SFX voices* and the active BGM voice. Therefore a cue started on an earlier tick does **not** retain an immutable earlier gain after a later volume change. Simply storing a per-event percentage and playing both cues at the end with their original gains would not model native active-voice retuning.

Unity current path: `SimulationTickDriver.StepOneTickInternal(FrameInputSet)` captures checksum then appends `SimulationWorld.PendingSounds` to `_publishedSoundEvents` at `SimulationTickDriver.cs:619-655,700-713`. The LocalFreeRun wrapper applies the current F11/F12 command after a successful tick at `566-609`. Actual `NTSDSoundPlayer.PresentSounds(...)` is called only by `DispatchPublishedSounds` in `LateUpdate` at `490-508,715-742`. Two successful ticks in one `Update` therefore enter the same list and start both voices later, after the second tick's volume adjustment. `NTSDSoundPlayer.cs:83-112` retunes already-playing pooled voices, but the earlier queued cue has not started yet. The worker publication path also applies the command before copying sound events into this list; it still dispatches in the later presentation call.

Confirmed first difference: **per-tick battle audio voice start/publication time**. Native begins a tick's battle voice before the next successful tick; Unity begins all queued voices together at LateUpdate. The intermediate gain/time window and possible native audio samples between adjacent tick submissions are the material observable risk. At the end of the second tick, formal `apply_volume_gains` can retune the first active voice to the latest percentage, so the earlier note that every cue must permanently keep a distinct per-tick gain was too strong. Audible magnitude and whether the window yields different output in a particular run remain unmeasured.

Next implementation gate: a separate Q10 Task/Change should test two accepted LocalFreeRun ticks in one outer Update with a sound on each tick and held F11/F12, asserting *when* each sound reaches the sink relative to each tick's volume application and checksum, then change publication only if the observed first difference persists through the real selected path. Preserve sound event order, checksum independence, suppression semantics, lifecycle stop, and worker no-Unity-API boundary. Do not add immutable per-event gain as a shortcut. After that, use a bounded selected-cue Play/audio capture and formal EXE comparison; BGM/WMA remains a separate owner/decode gate. Q10/O-03 and the overall alignment goal remain open.

No project script, DAT, image, WAV, Scene, Asset or nonbattle function was changed by this audit.
