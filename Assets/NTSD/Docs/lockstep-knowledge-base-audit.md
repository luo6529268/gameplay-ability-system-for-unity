## 4. 统一知识结论

### 4.1 帧同步同步的是输入事实，不是结果

正常战斗帧只传输并授权 `FrameInputSet`。位置、速度、HP、PP、命中、伤害、Buff、opoint、死亡和 AI 决策必须由同一 BattleKernel 根据相同初始状态、输入、顺序和 RNG 计算。

状态包只能出现在：

- 开局 bootstrap；
- 断线重连；
- 严重 desync 恢复；
- 观战或晚加入的起始点；
- 离线诊断与回放跳转。

不得在正常对局中周期性用服务器位置或 HP 覆盖客户端，然后仍声称这是同一套纯帧同步战斗真相。

### 4.2 逻辑、网络和渲染是三条频率

NTSD 固定：

- 战斗逻辑：30 Hz；
- 网络组包：独立配置，例如 15 包/秒、每包携带两个连续 30 Hz 帧；
- 渲染：60/90/120 Hz，读取已发布逻辑快照。

降低网络包频率不合并逻辑帧；提高渲染频率不多跑战斗 tick；CPU 执行耗时也不能改变 `SIM_DT`。

### 4.3 四个帧游标必须分离

客户端至少区分：

1. `latestLocalSampleFrame`：已采样并发送的本地目标输入帧；
2. `highestReceivedServerFrame`：收到过的最高权威帧，可能中间有洞；
3. `highestContiguousReadyFrame`：从已执行帧之后连续可消费的最高权威帧；
4. `localExecutedFrame`：BattleKernel 已真正完成的最后一帧。

不能用“收到过的最高帧”直接驱动追帧，否则中间缺帧会被跳过。

### 4.4 权威帧锁定后不可变

每个 `(sessionId, frameId, playerSlot)` 只有一个权威输入：

- 首次合法输入进入未锁定 inbox；
- 相同内容的重复包幂等接受；
- 不同内容的重复包记录冲突并拒绝；
- 帧截止后由服务器按房间规则补齐并锁定；
- 已锁定或已广播帧不能被迟到输入覆盖；
- 补齐规则与结果必须写入权威输入历史。

“后到的数据覆盖前到的数据”只适合某些普通缓存，不适合已经成为回放、checksum 和所有端共同事实的帧。

### 4.5 缺失输入策略是对局规则

候选策略包括：

- 严格等待：只用于最初协议正确性原型；
- 短 grace 内沿用上一帧 held、所有 edges 置零；
- neutral 输入；
- 服务器 AI 托管；
- 判定离线或结束连接。

最终策略、grace 帧数和切换点必须由服务器会话配置固定，进入 session fingerprint、输入历史和回放。客户端不能自行选择，也不能因本机卡顿临时改变。

### 4.6 Jitter Buffer 是状态机，不是一个 Queue

客户端权威帧缓冲至少包含以下状态：

```text
Priming
  -> Running
  -> WaitingForGap
  -> CatchingUp
  -> RecoveringSnapshot
  -> Running
  -> Faulted/Ending
```

- `Priming`：积累目标缓冲，不立即消费第一帧；
- `Running`：保持目标缓冲深度，正常 0/1 tick；
- `WaitingForGap`：下一连续帧缺失，只补发/等待，不跳帧；
- `CatchingUp`：连续帧已经 ready 且本地确实落后，按 CPU 预算有限追帧；
- `RecoveringSnapshot`：落后超出历史窗口或 checksum 分叉，恢复权威快照后重放；
- `Faulted`：协议冲突、资源指纹错误或恢复失败，显式停止。

### 4.7 追帧处理积压，不处理单机正常时间

必须区分：

- 逻辑时间：固定的规则时间；
- 墙钟时间：现实时间；
- 计算时间：CPU 实际耗时。

单机 `OfflineLocal` 没有服务器目标帧，正常 Unity `Update` 不应一次执行四个完整网络追帧 tick。网络追帧只在“连续权威帧已 ready 且 `localExecutedFrame` 落后目标缓冲”时发生。

每个可见帧的追帧次数和 CPU 时间都要有硬上限。持续追不上是容量失败，应优化算法、数据和 Unity API 使用，或进入快照恢复；不能无限 while，也不能改变 dt、跳过碰撞或减少战斗规则。

### 4.8 预表现不能提前产生战斗结果

NTSD 采用三层合同：

| 层 | 可做内容 | 禁止内容 |
|---|---|---|
| Input Echo | 按键/UI/轻音效/瞄准提示 | 修改角色 runtime |
| Intent Presentation | 本地起手、朝向预热、可撤销姿态、有限显示预测 | 扣 HP、生成权威 opoint、决定命中 |
| Confirmed Result | 根据确认逻辑事件播放命中、受击、死亡、正式技能和音效 | 反写 BattleWorld |

正式表现事件必须携带稳定事件键，用于重复包、追帧、回放和未来回滚的去重。恢复或重算时，逻辑事件历史可重建；音效、粒子和镜头不进入逻辑 checksum。

### 4.9 快照、输入历史和 checksum 是一套恢复系统

三者职责不同：

- `FrameHistoryRing`：逐帧保存不可变权威 `FrameInputSet`；
- `SnapshotRing`：周期性保存可版本化、可恢复的完整 BattleWorld；
- checksum：周期性检测状态是否一致，并按域定位首个分叉。

恢复流程固定为：

```text
验证 session/catalog/stage/profile/schema
  -> RestoreWorld(snapshot at S)
  -> 重放 S+1 ... target 的权威 FrameInputSet
  -> 比较 checksum
  -> 重建表现快照和事件去重游标
```

客户端本地快照可以作为诊断或临时缓存，但不能成为服务器信任的权威恢复源。

### 4.10 服务器是帧的授权方，也运行同一战斗核心

服务器职责不是另写一套“服务器伤害逻辑”，而是：

- 验证连接、身份、目标帧、序号和输入范围；
- 在统一截止点锁定完整 `FrameInputSet`；
- 调用同一个 `BattleKernel.StepOneTick`；
- 保存历史、checksum 和快照；
- 广播权威帧；
- 处理掉线、恢复和对局状态机。

一个房间内部串行；多个房间可并行到不同 worker/process。网络回调只入队，不能直接改 World。

### 4.11 协议与传输必须分离

高频帧数据需要：

- 固定宽度字段、schema/version、显式字节序和最大长度；
- `sessionId`、frame、player slot、input sequence；
- server sequence、ACK、重复/乱序去重；
- 最近若干帧冗余或可靠补发；
- 无分配或复用缓冲的序列化；
- 稳定协议 ID，优先代码生成，热路径不反射。

登录、匹配、房间和快照请求可使用 RPC/StreamingHub；每个 30 Hz 输入帧不应创建一次 RPC request/response/Future 上下文。具体 UDP、KCP、ENet、MagicOnion 或其他库要在 S0 之后按实测选型。

### 4.12 安全与反作弊边界

- 加密保护链路机密性与篡改门槛，但不能证明客户端诚实；
- 客户端不能上报“我已命中、造成多少伤害”作为权威结果；
- 两个客户端 checksum 不同不能靠多数投票判断谁正确；
- 服务器同核运行的 checksum、输入合法性、回放审计和快照是主要证据；
- 纯帧同步客户端通常拥有完整模拟信息，无法仅靠协议隐藏彻底解决透视；如未来需要强信息裁剪，必须重新评估玩法与同步模型，不能悄悄用 AOI 删除客户端计算所需战斗数据。

## 5. NTSD 明确采用的架构决策

1. 单机、回放、未来客户端和服务器共享唯一 `StepOneTick(FrameInputSet)`。
2. BattleKernel 固定 30 Hz，Unity wall clock 只属于 host policy。
3. 服务器运行同一 C# 战斗核心并授权不可变权威帧。
4. 输入、帧包、checksum、快照和资源指纹均版本化。
5. 客户端按连续 ready 边界消费，绝不跳过中间缺帧。
6. 追帧有 tick 上限、CPU 预算和快照恢复出口。
7. 正常战斗只同步输入；状态快照只用于 bootstrap、恢复、观战和诊断。
8. 表现采用 Input Echo / Intent / Confirmed Result 分层，强结果只由确认逻辑触发。
9. 高频协议使用流式消息、稳定 ID、代码生成与复用缓冲；控制面与数据面解耦。
10. 自研混合 ECS 负责数据布局和批量处理，但不替代确定性、空间算法、回放、快照或反作弊。
11. 单房间串行，多房间并行；不在首期并行修改同一 BattleWorld。
12. 正式战斗稳态以零托管分配为目标，容量在开局前封印。

## 6. 需要 NTSD 适配后采用的结论

| 通用经验 | NTSD 适配 |
|---|---|
| 全面使用定点数 | 先保持 C# 权威数值语义；用跨运行时 journal/checksum 找到实际分叉域后逐域迁移 |
| 20 Hz、15 Hz 或其他逻辑帧率 | NTSD DAT 与现有权威时序固定 30 Hz；低频只用于网络组包 |
| 缓冲 2～4 帧 | 作为测试起点，不是常量；根据 RTT、jitter、冲突率与手感决定 |
| 每次收齐所有玩家输入才推进 | 只用于 S0 严格原型；生产使用统一 deadline 和确定性缺失输入策略 |
| 本地移动预测 + 和解 | 等可恢复快照与真实网络测量完成后再决定；不与基础确定性迁移同批实施 |
| “无输入则状态不变” | NTSD 每个 tick 本身就是显式时间输入，状态机、速度、Buff、投射物和 AI 仍会推进 |
| 空间 AOI/四叉树 | 单机和服务器内部用于减少查询；不能裁掉 lockstep 客户端所需的完整战斗事实 |
| 单帧预算经验值 | 只作为告警思路；NTSD 以同口径 Editor/Player 实测 Avg/P95/P99 定门禁 |

## 7. 明确不采用的结论

1. 丢失攻击输入可以忽略，不补发。
2. 同一玩家、同一权威帧发生冲突时以后到数据覆盖先到数据。
3. 已锁定或已广播的权威帧被迟到输入修改。
4. 客户端发送位置、命中或伤害结果，服务器另写一套规则结算。
5. 正常战斗周期性用状态包覆盖位置、HP、Buff，同时仍把客户端模拟称为唯一 lockstep 真相。
6. 使用多数客户端 checksum 投票代替服务器权威模拟。
7. 认为传输加密可以阻止客户端作弊。
8. 用 `Time.deltaTime`、真实 CPU 耗时或动态 dt 改变逻辑规则。
9. 单机普通 Update 使用网络追帧循环，或网络追帧无限 while。
10. 为追帧跳过碰撞、Buff、AI、命中、opoint 或生命周期规则。
11. 让 Animator、Transform、Unity Physics、粒子或资源加载时机成为战斗真相。
12. 将客户端本地磁盘快照当作服务器可信状态。
13. 在当前基础 lockstep 中引入 Source/FPS 式服务器 hitbox 延迟补偿。
14. 直接照搬任一文章的传输库、帧率、阈值、缓存长度或性能数字。

## 8. 对统一方案的修订要求

`unified-battle-lockstep-ecs-server-architecture-plan.md` 必须包含并保持以下合同：

- 四个帧游标与连续 ready 定义；
- 权威帧不可变、幂等重复和冲突重复规则；
- Jitter Buffer 状态机；
- 缺失输入策略的会话所有权；
- backlog、有限追帧、容量失败与快照恢复出口；
- 正常输入同步与恢复状态同步的硬边界；
- 预表现三层和稳定事件键；
- FrameHistory/Snapshot/Checksum 的统一生命周期；
- 客户端与服务端会话状态机；
- 控制面/数据面、RPC/帧流的边界；
- 安全假设与明确拒绝项；
- S0 以前不绑定 transport，且不提前实现第二套战斗规则。

## 9. 本轮结论

知识库审计已覆盖 `网络游戏` 下全部 19 个独立主题，并将核心帧同步知识与状态同步、FPS 延迟补偿、UE 移动复制、AOI、RPC 和实时服务器案例分开处理。

审计结果支持当前总方向：先把 NTSD 单机战斗收敛为可重放、可快照、零 GC 的共享 BattleKernel，再通过同进程服务器验证权威帧、Jitter Buffer、checksum 和恢复，最后选择真实 transport。它不支持用“客户端结果上报 + 服务器状态覆盖”拼成第二套战斗逻辑，也不支持把 ECS 或追帧当作持续超预算的替代方案。
